## 2. Architecture retenue : deux authentifications indépendantes

**Master est l’autorité de session humaine** : il valide le challenge OTP, signe la preuve, gère le registre Redis et expose une introspection réservée aux services autorisés. BFF et API Tenant exigent chacun une introspection positive du bearer original. Ils ne font pas confiance à un objet principal transmis par le navigateur ou simplement recopié du BFF.

La vérification HMAC est effectuée par Master pour le compte de chaque consommateur : le BFF vérifie la session par introspection autoritaire, puis l’API la vérifie indépendamment de bout en bout. Cela évite de distribuer le secret d’émission aux processus Tenant et de conserver deux autorités de signature. Ce n’est pas une nouvelle preuve BFF→API par requête (option B écartée). Aucun cache positif inter-requêtes ne prolonge une autorisation après révocation.

Parcours manager :

1. Le Cloud demande le challenge de connexion existant. Master résout lui-même compte et tenant, vérifie leur disponibilité et conserve le challenge dans Redis avec TTL de 5 min, digest du code et limites d’essais/envois. Le navigateur ne choisit pas l’identité à signer lors de la vérification.
2. Sur vérification, Master revalide le compte et son rattachement via les opérations tenant explicites existantes. Une opération atomique Redis consomme le challenge attendu et inscrit la nouvelle session. Aucune réponse contenant une session n’est renvoyée avant succès de cette opération.
3. Master renvoie le profil et `access_token`, `token_type: Bearer`, `expires_in` ; le BFF relaie ces champs dans son enveloppe actuelle. Il ne signe plus de token à partir du profil reçu.
4. Le Cloud transmet le bearer. Le BFF introspecte, vérifie tenant demandé et mode, puis transmet le **même bearer humain** à l’API dans un en-tête interne réservé.
5. L’API authentifie le service applicatif, introspecte la preuve humaine, compare le tenant à la cible de routage, puis laisse le middleware tenant V01 existant établir sa portée. Dans cette portée, elle recharge l’utilisateur actif, ses rôles et les relations utiles, puis autorise la ressource et l’action.

La résolution du principal précède toute admission SQL métier sous une cible fournie par le navigateur. Les recherches de compte réalisées par Master utilisent ses frontières tenant explicites existantes ; aucune sélection globale ni modification de V01. Un middleware dédié aux chemins mémos/médias s’insère entre `ServerAuth` et le middleware tenant (`packages/api/src/tenant/app.ts:160–166`), avec contrôle complémentaire après résolution du tenant. Il ne déplace pas le middleware V01 et n’étend pas arbitrairement l’authentification humaine aux autres routes.

**Preuve de service :** conserver les credentials et signatures du client API existant. `ServerAuth` privilégie actuellement `Authorization` hors `/integrator` (`middle/server-auth.ts:255–280`) ; ne pas le remplacer par le bearer humain. Proposition : `X-Toke-User-Session` sur le lien interne, et `X-Toke-Integrator-Session` + `X-Toke-Integrator-Context` en mode délégué. Le BFF ignore/supprime les variantes internes entrantes et les reconstruit depuis le bearer public vérifié. L’API vérifie toujours les preuves, même si un appelant peut joindre directement son port. Aucun en-tête `X-User-Guid` ne suffit. Refuser les preuves de modes mélangés ou contradictoires.

`ServerAuth` comporte un retour anticipé root (`:69`) : cela ne doit dispenser aucune route mémos du principal humain. La nouvelle vérification ne dépend pas uniquement de la présence de `req.client` produite par cette branche. Le droit technique de joindre une API et le droit d’agir sur un mémo restent deux conditions cumulatives.

### Preuve et registre proposés

- Format conservé : `base64url(payload).base64url(HMAC-SHA256(payload))`. Payload v2 strict : `v`, `kind: manager`, `iss`, `aud`, `sid`, `tenantGuid`, `userGuid`, `iat`, `exp`, `kid`. GUID canoniques en chaînes ; `sid` issu de 32 octets cryptographiques. Pas de sélection d’algorithme par le client.
- Valeurs fixes proposées : `iss=toke-master`, `aud=toke-user-session`. Cette audience n’accorde aucun droit générique aux autres modules. Signature, taille maximale, encodage, types, version, émetteur, audience et dates sont validés. `exp <= iat + 86400`, pas de prolongation glissante ni refresh implicite. Expiration stricte ; tolérance d’horloge de 30 s uniquement pour un `iat` futur, sans prolonger `exp`.
- Registre `toke:auth:v2:session:<hash(sid)>` : version, digest du token, identité immuable, émission/expiration absolues, état `active|revoked`, date de révocation et version de clé. Aucun mot de passe, OTP clair ou token bearer stocké. TTL jusqu’à expiration ; la date est également contrôlée à la lecture.
- Création unique `NX`, jamais recréation sur introspection. Le digest et les claims doivent correspondre au registre ; HMAC valide avec entrée absente => refus. Écriture/lecture sur l’autorité Redis primaire, pas sur une réplique potentiellement en retard.
- La signature seule n’accorde rien : signature **et** registre **et** tenant **et** utilisateur actif **et** autorisation métier. Principal en mémoire immuable, limité à la requête et distinct de la portée ALS V01 : `{mode, sessionId, tenantGuid, effectiveUserGuid, actor, contextId?, delegationScopes?, exp}`.
- Révocation atomique et idempotente ; tombstone conservé jusqu’à l’expiration, sans réactivation. Publication d’un événement minimal de révocation après modification autoritaire. Aucun token dans les logs, erreurs, URLs, traces Axios ou événements.

Le défi OTP manager doit quitter le cache fichier **pour ce parcours seulement**. Stockage partagé, limitation des tentatives et consommation+inscription par script atomique, ou transaction Redis équivalente vérifiée. Pour Redis Cluster, les clés manipulées ensemble doivent partager un hash-slot ; ne pas supposer que le script multi-clés actuel serait portable. Une topologie Redis primaire commune est la cible initiale proposée, à approuver avant de coder. Les autres familles OTP (`OTPCacheService`, QR, intégrateur) ne deviennent pas des moyens alternatifs d’émettre un token manager.

La transition doit également fermer l’exposition des données de challenges manager via `/tenant/cache/stats` (`tenant.route.ts:1806`) et les logs de codes (`:1623`, `:1780`) : statistiques agrégées seulement pour un service d’administration explicitement habilité, aucun profil/challenge exploitable retourné. Ne pas élargir cet ajustement à un audit général des routes OTP.

## 4. Sessions, logout et intégrateurs

### Cycle de vie manager

Expiration maximale **24 h dès émission**. Aucun renouvellement par navigation ni donnée locale valable sept jours. Token historique sans version/registre => 401 et nouvel OTP ; pas de conversion d’un GUID, d’un profil en cache, d’un ancien token signé ou d’un code QR en nouvelle session.

Proposition d’API de cycle de vie : `POST /tenant/session/logout` public BFF, relayé à une route Master réservée au service. Révoque uniquement la session présentée et reste idempotent pour un token connu révoqué/expiré ; aucune identité à révoquer reçue dans le body. Endpoint interne d’introspection `POST /auth/session/introspect`, corps contenant la preuve et le tenant attendu, jamais journalisé. Réponse minimale : principal, expiration et statut ; aucun secret ni profil complet. La route Master vérifie aussi l’habilitation du service appelant.

Le Cloud capture la preuve de logout, invalide immédiatement la génération, ferme ses sockets et purge les états mémos, puis termine la révocation avec la preuve capturée. Une panne distante retourne 503 et l’interface indique que la révocation serveur n’est pas confirmée ; elle ne restaure pas le cache et ne prétend pas que le bearer volé est invalidé. Propager le nettoyage aux autres onglets via un événement local sans token. Sur 401 : purge/reconnexion ; sur 403 : refus métier sans usurpation de profil ; sur 503 : pas de fallback anonyme, pas de nouveau token, pas d’affirmation « session révoquée ».

La révocation est linéarisée au changement atomique du registre : les admissions suivantes sont refusées. Une requête ou un octet déjà autorisé/envoyé peut terminer ; ce contrat ne promet pas l’annulation rétroactive du SQL, d’un téléchargement ou d’un commit engagé. Ne jamais rejouer automatiquement une écriture après erreur réseau/commit incertain. Pour les streams, interrompre les émissions futures dès notification de révocation/expiration, sans prétendre reprendre des octets déjà transmis.

### Délégation intégrateur distincte

Conserver la session opaque actuelle (8 h, donc sous le plafond 24 h) et la sélection de contexte (1 h, bornée par l’expiration restante de la session). L’API introspecte le couple session/contexte directement auprès de Master ; BFF `src/tools/integrator.delegation.ts` ne constitue pas à lui seul une autorisation de l’API.

Principal délégué : acteur réel = identité intégrateur vérifiée (email autorisé + ID opaque de session), profil effectif = userGuid tenant vérifié, identifiant de contexte, expiration, scopes de délégation. Aucun token manager n’est fabriqué. Les logs d’action conservent acteur réel et effectif, sans réécrire l’auteur historique du mémo ni exposer l’email intégrateur aux autres participants.

Le code actuel autorise un email figurant dans `INTEGRATOR_EMAILS` à choisir un profil MANAGER/ADMIN-RH actif ; il ne contient pas de mandat tenant/action finement borné. **D7 proposé :** registre/configuration explicite de grants intégrateur→tenants→profils autorisés→scopes, administré hors navigateur ; absence de grant => refus. Pas de wildcard implicite à partir de l’allowlist. Le périmètre des grants doit être fourni et approuvé par l’utilisateur ; l’implémentation ne peut pas inventer une délégation générale pour conserver les accès actuels.

Les droits effectifs sont l’intersection du grant, des droits actuels du profil et de l’ACL du mémo. Recharger activité et rôles du profil à chaque opération, pas depuis les snapshots Redis `user/tenant`. Retrait de l’allowlist ou du grant => refus. Vérifier aussi l’état du contexte et de sa session parente pour chaque action, ticket et émission ; nettoyer les clés enfants ne suffit pas à révoquer.

Changement de profil : atomiquement invalider l’ancien contexte et créer le nouveau après vérification du grant ; anciens sockets et tickets deviennent invalides. Un contexte ne survit pas au logout intégrateur. Mode Cloud dédié avec état de délégation vérifié : corriger ultérieurement l’appel de `integratorStore.ts:97` à `setAuthData` sans token, sans rendre la connexion manager permissive. Ne pas employer le logout manager pour révoquer accidentellement toute la session intégrateur pendant une simple sortie de profil.

## 5. Médias et temps réel

**Médias :** le fichier reste dans son répertoire tenant actuel. À l’upload, le serveur crée un bail temporaire privé lié à tenant, session, utilisateur et fichier canonique ; contrôle préalable à multer et bornes taille/type. Pour joindre un nouveau fichier, l’API vérifie ce bail et son propriétaire. Pour un fichier déjà lié, vérification de la référence persistée au mémo et de son ACL ; une URL insérée dans le body ne crée pas un droit. Ne pas effacer automatiquement des fichiers historiques ou orphelins.

Proposition de contrat minimal à approuver : conserver les enveloppes d’upload et le proxy BFF `GET /memo?url=…`, ajouter `memo_guid` pour un téléchargement de fichier lié. L’API `/upload/f/:filename` exige ce même contexte de ressource et la preuve humaine ; le Cloud charge le média avec son bearer via le BFF puis un blob local. Une navigation/image HTML directe sans bearer n’est plus admise. Brouillon : bail d’upload vérifié au lieu de `memo_guid`, accessible seulement à la session créatrice. Aucun token de session dans l’URL.

Le BFF n’accepte que des références canoniques de l’API de fichiers connue, reconstruit la destination depuis la configuration interne et refuse URL externe, redirections, traversée, noms ambigus et chemins d’un autre tenant. Pour les médias historiques : résoudre le lien réellement stocké dans le contenu du mémo autorisé ; aucun déplacement de fichier ni réécriture massive. Lien impossible à relier de façon fiable => refus documenté, revue manuelle. Vérifier ultérieurement qu’aucun `express.static`, proxy ou CDN ne sert les mêmes fichiers en contournant l’API. Les autres usages éventuels de `/upload` devront être inventoriés avant modification de cette route partagée ; ils ne doivent pas garder un accès alternatif aux pièces mémos.

**Temps réel :** conserver le pont Cloud→BFF→API ; tickets opaques courts, usage unique, liés au mode, session, contexte délégué, tenant et profil. TTL proposé 60 s au maximum et jamais au-delà de la session. Création et consommation atomiques dans Redis, avec namespaces distincts pour les deux étages ; pas de réutilisation de la Map comme autorité. À reconnexion, demander un nouveau ticket sous la preuve encore valide ; le pont ne peut plus rafraîchir un ticket avec le seul userGuid capturé (`memo.socket.bridge.service.ts:193–204`).

À l’ouverture, à la réception d’une action, avant chaque émission de notification et lors d’une reconnexion : vérifier l’état autoritaire et les droits pertinents ; pendant une panne registre, suspendre/refuser les émissions et fermer les sockets authentifiés concernés. Une vérification périodique bornée accélère la fermeture physique si le pub/sub est perdu, mais ne remplace pas le contrôle avant émission. Timer d’expiration et canal de révocation ferment sockets BFF et amont. Les événements mémos restent des invalidations minimales ; ne pas envoyer de contenu, de liste de participants ou d’identité intégrateur à un destinataire devenu non autorisé.

Les Map de sockets peuvent rester locales comme inventaire technique, pas comme registre de validité. Plusieurs processus nécessitent une diffusion interprocessus des invalidations et révocations. Proposition : pub/sub Redis minimal via `ioredis` déjà présent dans l’API, connexions abonnées séparées, identifiant d’événement/déduplication ; chaque processus contrôle puis émet sur ses sockets locaux. Pas de promesse de livraison exactement une fois ; resynchronisation REST autorisée après reconnexion. Le polling Socket.IO conservé exige de l’affinité Engine.IO au reverse proxy ; ni le registre partagé ni pub/sub ne la remplacent. Aucun adaptateur Redis Socket.IO n’est présumé installé.

## 6. Redis, configuration et disponibilité

L’intégration Master existante utilise `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD` et `maxRetriesPerRequest:2`. Ce n’est pas la preuve de l’existence d’un Redis partagé, persistant ou correctement protégé en production. Prévoir une configuration explicite de l’autorité auth : adresse/port/base/namespace communs, ACL et TLS selon le réseau, délais bornés et disponibilité observée. Pas de fallback sur `localhost` en environnement de release si l’autorité attendue est absente. Ne pas créer un registre par worker PM2.

Master seul écrit les sessions/grants et signe ; BFF/API interrogent ses endpoints autorisés. Si le temps réel utilise directement Redis, droits limités aux tickets et canaux nécessaires ; aucune possibilité de déclarer une session active. Le BFF devra recevoir un client Redis explicite ou un client interne de tickets fourni par Master ; **recommandation** : client interne Master pour émission/consommation des tickets, abonnement Redis limité pour les invalidations. Confirmer le packaging du BFF avant ajout éventuel d’une dépendance directe ; aucune installation dans cette phase.

`USER_SESSION_SECRET` devient une clé d’autorité Master, chargée hors dépôt ; versions de clés explicites, clé inconnue refusée, validation de configuration au démarrage, pas de génération aléatoire différente par processus. Rotation coordonnée ; seules les clés encore autorisées et sessions inscrites restent admissibles jusqu’à expiration. Ne lire ni reproduire les secrets actuels dans les tests/rapports.

Panne Redis/introspection : 503 fermé, zéro mutation métier, aucun repli sur signature locale seule. Entrée absente/expirée/révoquée : 401. Tenant ou action interdits : 403 ; les ressources hors visibilité peuvent retourner 404 uniforme pour éviter leur énumération. Erreurs techniques et invalidité ne doivent pas être confondues par les proxies.

La durabilité des révocations est un prérequis : un failover ou une restauration Redis en retard peut ressusciter un état `active`. Interdire les lectures de répliques en retard, vérifier persistance/failover ; après rollback/reset/restauration non prouvée du registre, changer l’époque/clé d’authentification de façon coordonnée et forcer OTP avant réouverture. Aucun mécanisme applicatif mémoire ne prouve à lui seul l’absence de perte d’une révocation acquittée.

## 11. Contrat métier finalisé — étape B (9 novembre 2026)

### 11.1 Deux décisions indépendantes — approuvé

Le responsable habilité valide ou rejette le mémo. Séparément, un acteur habilité conserve les pointages ou demande une correction explicite, justifiée et tracée. Ni validation, ni rejet, ni réouverture, ni révocation ne déclenchent de correction implicite. Une correction effective demeure après rejet/réouverture ; seule une nouvelle rectification explicite peut la remplacer. Aucun fallback planning lorsque la correction manque. Le planning peut fournir une suggestion à confirmer, jamais une décision automatique au titre du mémo.

La conservation est une intention explicite à tracer, sans écriture horaire. La validation seule reste une commande valide : elle n’affirme pas que le manager a choisi « conserver ». L’interface présente les deux décisions séparément. Une nouvelle approbation ne rejoue aucune correction, quel que soit le cycle. Les valeurs brutes connues sont conservées et toutes les corrections successives liées ; une valeur brute historique perdue est signalée inconnue, jamais reconstruite par supposition.

### 11.3 Responsabilité — approuvé

Résoudre à la **soumission** pour le collaborateur concerné (auteur salarié ou cible du mémo manager/système), à l’heure serveur, puis figer le responsable et la provenance. Un brouillon ou échange PENDING n’est pas une preuve de responsabilité finale. Un mémo créé directement SUBMITTED est résolu dans sa transaction de création.

1. Collecter les relations DIRECT_REPORT actives, datées, non cycliques et cohérentes, vers un manager actif habilité ; dédupliquer par personne. Un responsable direct fiable unique est prioritaire, même si groupes ou assigned_by divergent.
2. Sans direct fiable et sans concurrence non résolue au niveau direct, retenir l’unique manager habilité des groupes actifs dont le collaborateur est membre actif. Plusieurs groupes dirigés par la même personne donnent un seul candidat ; plusieurs personnes restent en concurrence.
3. Absence de candidat fiable, conflit au niveau prioritaire ou structure impossible à certifier : conserver le mémo « Responsable à désigner ». Une concurrence entre directs ne se résout pas par un groupe. Un lien invalide est diagnostiqué ; on ne choisit jamais le plus récent ou le premier résultat pour masquer un conflit.
4. assigned_by est un indice historique, sans pouvoir de nomination ni veto sur un direct fiable. Les relations non DIRECT_REPORT ne prouvent pas la supervision. Les helpers actuels prenant le premier groupe ou tout type de relation doivent être remplacés pour ces usages.

Proposition de compatibilité groupes : conserver `member.active !== false` (champ absent admis historiquement), avec groupe non supprimé et comptes actifs ; tester explicitement ce cas. Ne pas inventer des dates de sortie historiques.

Gestion directe, gestion de groupe, supervision et responsabilité décisionnelle sont quatre capacités distinctes. La supervision remonte uniquement les liens DIRECT_REPORT actifs du responsable, sans cycle ; elle ne donne pas le droit de décider. Un changement d’organisation ne réattribue pas un dossier. Si le responsable perd son habilitation, bloquer ses décisions et demander un transfert autorisé et historisé, sans effacer sa désignation antérieure.

### 11.4 « Responsable à désigner » sans nouveau statut SQL

Proposition additive : état de responsabilité séparé `UNRESOLVED`, `ASSIGNED`, `REVIEW_REQUIRED`, colonne responsable nullable, provenance versionnée, cycle/version et référence du dernier événement. Les anciens mémos restent distingués par une projection absente, pas assimilés à une attribution certifiée. Le plan propose une table d’extension pour éviter toute réécriture des lignes historiques à la migration.

SUBMITTED reste `submitted` ; PENDING garde son tour de réponse ; APPROVED/REJECTED/REVOKED ne changent pas. Le libellé « Responsable à désigner » est un badge de responsabilité, accompagné du statut réel, pas un sixième statut. L’absence de responsable ne refuse ni ne perd une soumission humaine ou automatique. Elle interdit décision et supervision dérivée ; elle n’élargit pas la lecture au tenant.

Listes, compteurs et pagination appliquent ACL, statut et filtre de responsabilité **avant** offset/limit ; jointure externe univoque sur l’extension, jamais jointure multipliant les lignes par événement. Les files de décision excluent les responsabilités non résolues ; une file de désignation ne sera ouverte qu’à une capacité explicitement définie. Notifications : aucun destinataire manager arbitraire, aucune diffusion globale ; information au participant autorisé et éventuelle file habilitée future. Les tâches automatiques conservent le dossier et ne l’escaladent pas vers un validateur de substitution.

| État et commande | Transition / garantie |
|---|---|
| SUBMITTED, responsable actif, décision sur cycle/version attendus | APPROVED ou REJECTED ; événement obligatoire même sans message ; aucun effet horaire. |
| APPROVED/REJECTED, commentaire du supérieur autorisé | Commentaire + REOPENED + SUBMITTED atomiques ; cycle incrémenté une fois, responsable inchangé, nouvelle demande de décision. |
| SUBMITTED, commentaire simultané du supérieur | Conserver le commentaire ; même cycle, version incrémentée ; pas de seconde réouverture. |
| PENDING, commentaire de supervision | Commentaire uniquement ; conserver le tour de réponse. |
| Toute correction explicite | Commande distincte, version des cibles contrôlée ; aucun changement du statut du mémo. |
| Transfert autorisé | Changement explicite du responsable, provenance et événement ; invalider les commandes anciennes par version, pas par réouverture automatique. |
| REVOKED | Aucune réouverture automatique ; commentaire de supervision refusé en attendant politique explicite. |

Toutes les mutations sont sérialisées sous verrou du mémo, avec relecture des droits dans la transaction tenant V01. La décision exige cycle **et version** attendus : un commentaire dans le même cycle peut rendre une décision obsolète. Conflit => 409, relire et confirmer ; aucune relance automatique d’une décision. Deux commentaires concurrents sont ajoutés sous verrou sans remplacement de tableau JSONB ; chacun reste conservé. Après décision puis commentaire : réouverture ; après commentaire puis décision portant l’ancienne version : refus. Notifications uniquement après commit, avec déduplication durable.

### 11.6 Journal, historique et corrections

Retenir une table d’événements en ajout seul, pas le JSONB mutable comme source d’audit. État courant et événement correspondant sont écrits dans une seule transaction. Identité serveur, auteur effectif, acteur délégué réel éventuel, responsable instantané, résultat, date serveur, cycle/version et liens causaux sont obligatoires selon le type. Le plan définit contraintes, privilèges, idempotence et journal séparé des corrections.

Les historiques existants sont conservés tels quels. Une première opération peut enregistrer un **instantané observé maintenant**, explicitement incomplet ; elle ne crée pas une ancienne décision datée fictivement. validator_user reste un champ historique, jamais le responsable certifié par défaut. Les anciens mémos corrigés gardent leurs effets ; ni rollback ni nouvelle application automatique. Migration additive proposée, sans `sync()` existing, sans backfill et sans exécution même fictive.

### 11.7 D1–D6 et limites restantes

- **D1** : consultation participant légitime ou supérieur courant du responsable certifié ; médias, agrégats, recherche et événements utilisent le même périmètre. L’analyse tierce générale reste fermée sans droit explicite. Lu/non lu superviseur doit utiliser une lecture par utilisateur autorisé, sans ajouter artificiellement un participant.
- **D2** : création manager sur collaborateurs directs ou membres actifs de ses groupes ; soumission conservée même sans responsable. La cible de routage n’est pas une preuve de responsabilité.
- **D3** : édition autorisée à l’auteur dans les états permis ; aucun champ protégé éditable via PUT ; aucune suppression ordinaire du journal ni cascade supprimant ses preuves. Suppression fonctionnelle à rendre compatible avec la conservation.
- **D4** : réponses selon le tour existant ; commentaire du supérieur distinct et réouverture transactionnelle sur décision terminale ; affichage de toutes les décisions connues, avec avertissement d’incomplétude historique.
- **D5** : décision réservée au responsable actif certifié, sur SUBMITTED et cycle/version courants ; validation en lot soumise aux mêmes règles, aucun helper de correction appelé. Conservation/correction sont des actions séparées, jamais déduites du résultat.
- **D6** : supervision et demande de réexamen sans transfert ; neutraliser l’ancien remplacement de validator_user dans escalade humaine/automatique. Le transfert est une commande spécifique avec habilitation encore à définir.

**Points encore bloquants pour les seules fonctions concernées :** qui peut désigner/transférer, sur quel périmètre et vers quels candidats ; qui peut corriger les pointages (le manager habilité est admis, mais sa capacité précise et celle d’autres acteurs restent à définir), sur quels états et avec quelle référence de décision lorsqu’aucune décision n’existe ; politique d’auto-validation quand auteur manager et responsable coïncident ; accès des anciens participants/responsables après transfert ; durée de conservation et procédure exceptionnelle d’effacement. Ne pas inventer de rôle ADMIN-RH omnipotent. Ces points ne remettent pas en question la priorité du direct, SUBMITTED, la table dédiée ou la persistance des corrections, désormais approuvés. D7 reste entièrement distinct.
