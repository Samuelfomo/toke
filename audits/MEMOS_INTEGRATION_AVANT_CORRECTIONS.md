## Authentification et autorisations

- OTP : BFF `routes/tenant.route.ts:118` extrait user.guid/tenant.guid de la réponse de vérification et émet le token HMAC (`tools/user.session.ts:27`). Cloud `userStore.ts:264` exige access_token avant de modifier l'état et l'enregistre en auth_token ; Fetch.Client.ts l'ajoute en Bearer. Configuration requise USER_SESSION_SECRET >=32 octets, **valeur non consultée**. Absence provoque erreur d'émission ; validation renvoie null.
- Validation : signature timingSafeEqual, taille bornée, identités non vides, iat/exp entiers, futur refusé et durée maximale 24h. Signature altérée et expiration réellement testées avec source exécutée et horloge fictive. Pas de registre de révocation/jti ; logout navigateur ne révoque pas un token copié, confirmé localement. Aucun mécanisme affaibli pour compenser.
- **Risque démontré au niveau middleware** : TenantConfig.authenticate accepte seulement un x-api-client non vide et continue sans token (`tenant.config.ts:10`). /list, détail, création, réponses, validation, médias et tickets temps réel utilisent ce garde ; /read ajoute authenticateUser. BFF app.ts:190 ajoute la délégation intégrateur, pas une authentification utilisateur générale. Un GUID de superviseur connu peut être présenté au BFF sans prouver être cet utilisateur. Tests exécutés du middleware ; exploitation HTTP complète avec API externe non exécutée. ACL/reverse proxy réels non inspectés.
- L'API authentifie le client applicatif via ServerAuth puis sélectionne le tenant ; cela ne certifie pas l'utilisateur final. /read API fait confiance au user_guid reçu du client applicatif. Le BFF authentifié est donc une frontière essentielle. V01 empêche une connexion étrangère à la portée, mais ne rend pas légitime une sélection de tenant demandée par un appelant non authentifié.
- Liste : participation auteur/cible/validateur, pas descendants hiérarchiques. /read reprend ces trois participants et ajoute utilisateur actif. /list ne vérifie pas son activité ; sans supervisor, le handler API n'applique pas cette restriction de participation (BFF l'exige). Définir les droits hiérarchiques explicites, sans élargir implicitement la consultation à toute l'entreprise.
- Sessions historiques : authData restauré peut ne pas contenir auth_token ; /read refuse 401, UI peut rester connectée. authData est conservé 7 jours (`userStore.ts:163`), token 24h ; pas de refresh/renouvellement automatique observé. Intégrateur : Fetch.Client privilégie son token Bearer, dont le format ne correspond pas nécessairement aux sessions HMAC à deux segments acceptées par authenticateUser ; parcours délégué /read à valider, pas déclaré compatible.

## Cache : défaut reproduit, pas seulement hypothétique

`memo-contract-review.cjs` exécute les vrais stores Vue/Pinia et le plugin installé, avec réseau remplacé par une promesse contrôlée et stockage mémoire. Une requête A démarre, logout est appelé, clearCache est même appelé explicitement, puis la réponse A arrive : **memos est repeuplé**. clearCache ne change pas _loadPromiseKey et n'invalide pas toutes les opérations détail/temps réel. Logout ne nettoie que teamStore (`userStore.ts:355`), clé de requête mémos sans tenant (`memoStore.ts:245`).

Deuxième preuve : `persist.paths: []` (`memoStore.ts:467`) est ignoré par pinia-plugin-persistedstate installé, qui traite pick/omit. `$persist()` conserve effectivement memo-A dans memo-store. La configuration réelle du plugin est activée dans main.ts. Risque : données A encore accessibles dans le navigateur après déconnexion/changement de session ; **aucun croisement SQL observé**. Les permutations de navigation complète A→B restent à compléter, pas présentées comme exécutées.

## MemoReads et migration proposée

Définition `database/data/memo.reads.db.ts:5` : id BIGINT auto-incrémenté, memo_id/user_id INTEGER NOT NULL avec FK CASCADE vers tk_memos/xa_users, read_at DATE Sequelize (TIMESTAMPTZ PostgreSQL), index unique (memo_id,user_id). Le nom physique est tk_memo_reads ; le bootstrap du modèle réel passe dans A/B.

Proposition explicite : [MEMOREADS_MIGRATION_FICTIVE_PROPOSITION.sql](./MEMOREADS_MIGRATION_FICTIVE_PROPOSITION.sql). **Non exécutée et non encore validée : ce n'est pas un artefact prêt production.** Le script refuse les bases hors A/B et le socket hors cluster V01/TCP actif ; il n'est donc volontairement pas utilisable en production en l'état.

Stratégie : transaction dédiée par base, verrou advisory et timeouts, création additive si absente, aucune mise à jour/backfill des mémos ou faux historique de lecture. Vérification des types, NOT NULL, PK, FK et index ; objet incompatible => exception/rollback, jamais DROP/ALTER réparateur. Un second passage doit être sans changement de données. Des variantes légitimes déjà présentes nécessitent classification manuelle et adaptation explicitement approuvée ; CREATE IF NOT EXISTS seul ne prouve pas la compatibilité.

Avant : métadonnées/PK des parents, permissions propriétaire et séquence, schéma/search_path, table ou index homonyme, absence de doublons/orphelins si table déjà présente, validité/defaults/contraintes supplémentaires. Après : mêmes données et objets parents, FK/index valides, ACL applicative SELECT/INSERT/UPDATE + séquence, upsert sous rôle tenant réel, seconde passe, empreintes catalogue. Le script de proposition couvre une partie de ces contrôles ; ACL, variantes historiques et essais idempotence/échec sont encore bloquants. Aucun contrôle de données client effectué ici.

Table absente : existing V01 marque le modèle indisponible sans DDL ; les autres tables compatibles restent accessibles. Le GET liste d'un utilisateur ayant des mémos appelle _readStatuses et échoue alors, /read échoue également. Une liste vide évite cette lecture. Le test PG a retiré la table **dans une transaction de fixture annulée** : les lignes mémos historiques restent consultables par modèle, le SQL de statuts échoue, rollback restaure table/lectures. Ce n'est pas une migration exécutée ni une recette HTTP complète de ce cas.

Déploiement futur : vérifier/autoriser la migration indépendamment de V01, rendre chaque base prête avant activation de ces consommateurs, revalider les générations/caches de métadonnées selon procédure manuelle. Pas de fallback fabriquant des statuts lus. Rollback code : conserver la table additive et ses lectures ; aucun DROP automatique ni restauration des données par retour Git.
