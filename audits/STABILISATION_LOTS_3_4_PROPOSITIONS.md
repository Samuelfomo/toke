# Toké — lots 3 et 4 soumis à approbation

Ces propositions ne sont pas implémentées. Aucun changement des tokens, des contrats d'authentification, des permissions ou du provisioning effectué pendant les lots 1–2. V01, ses gardes et existing sans DDL restent actifs.

## Lot 3 — principal utilisateur vérifié pour tous les accès mémos

**Recommandation :** une même chaîne de vérification sur liste, détail, statuts de lecture, création, contenu/réponse, validation/rejet/révocation/escalade, pièces jointes, téléchargement et ticket/socket mémos. Le header tenant et les GUID du payload ne constituent jamais une preuve d'identité. Réutiliser les sessions signées existantes comme point de départ ; toute extension ci-dessous demande accord explicite.

1. BFF : construire un principal immuable `{tenantGuid, userGuid, sessionId, actorType, delegationId?}` après vérification de signature, expiration, tenant et révocation. Charger l'utilisateur actif côté API tenant. Imposer le tenant du principal à getApiClient. Réserver les identifiants de filtre aux ressources autorisées ; rejeter une identité d'action différente, au lieu d'agir au nom de ce GUID. Aucun chemin anonyme sensible de compatibilité.
2. API : transmettre le principal sur le lien BFF→API avec une preuve interne signée et bornée, distincte du body client ; lier tenant, acteur, méthode, chemin, empreinte du body, expiration et nonce anti-rejeu. Rejeter les headers d'identité externes non signés. Le client applicatif ServerAuth reste vérifié ; il n'est pas assimilé à un utilisateur final. Une identité racine applicative ne dispense pas des permissions mémos. Les clients intégrateurs directs doivent avoir un contrat d'acteur explicitement autorisé ; pas de bypass générique à leur profit.
3. Centraliser une politique réutilisée par REST, SQL de liste/détail, média et Socket.IO : participation auteur/cible/validateur déjà admise ; utilisateur actif ; transitions existantes inchangées. Pour création/validation, vérifier le rôle et l'affectation/délégation attendus. **Ne pas accorder automatiquement tous les mémos des descendants** : la hiérarchie sert à contraindre une opération légitime, pas à étendre la visibilité. Les TODO actuels de POST /manager doivent devenir contrôles. Une décision métier reste nécessaire sur les actions exactes de chaque rôle et sur la représentation de hiérarchie déjà disponible.
4. Médias : rattacher chaque pièce au mémo accessible et au tenant ; accès par URL seul insuffisant. Upload sous principal actif, ticket temporaire ou référence propriétaire ; aucun téléchargement arbitraire d'un chemin d'un autre tenant. Le temps réel authentifie le même principal et filtre les destinataires autorisés.

**Sessions proposées :** ajouter un identifiant aléatoire de session à une nouvelle version du token signé et un enregistrement de validité/révocation avec TTL dans le Redis déjà utilisé, espace de clés spécifique, contenu minimal. Stocker le hash d'identifiant si approprié, jamais le token complet dans les logs. Une indisponibilité du registre bloque les opérations sensibles ; elle ne les rend pas anonymes. Fixer 24h maximum initialement pour conserver la durée serveur actuelle ; pas de refresh silencieux décidé dans ce lot. 401 à expiration => purge du cache local et nouvelle connexion OTP. Logout révoque la session et ferme ses sockets ; changement de profil invalide la délégation. Les sockets longues doivent revalider la session/révocation, pas seulement à l'ouverture.

**Sessions historiques :** tokens sans sessionId ou sessions sans token => reconnexion contrôlée au basculement, avec message clair et conservation uniquement des préférences non sensibles. Pas de conversion d'un GUID localStorage en preuve de connexion. L'ancien authData de sept jours n'étend pas le token de 24h. Une sortie de navigateur nettoie immédiatement le cache même si la requête de révocation échoue ; informer que le serveur n'a pas confirmé la révocation.

**Délégation intégrateur :** ne pas demander un OTP du manager ni fabriquer un token manager depuis son GUID. Le Master valide intégrateur, tenant, profil, droits et durée de délégation ; le BFF construit un principal délégué conservant acteur réel et profil effectif, avec audit et révocation liés au contexte. Le contrat Cloud d'entrée en profil doit distinguer délégation vérifiée et session manager. Incompatibilité locale confirmée à la lecture : `integratorStore.ts:97` appelle setAuthData sans access_token alors que userStore l'exige. Sa correction fait partie de l'accord lot 3, pas d'un assouplissement de setAuthData dans le lot 1.

**Fichiers envisagés :** backend tenant.config.ts, user.session.ts, routes tenant/memos, services API client/user/memo.socket.bridge, délégation intégrateur ; API middle principal et routes/service d'autorisation mémos, accès média/realtime ; Cloud userStore/Fetch.Client/auth et integratorStore. Le lot 1 n'a ajouté qu'une génération locale de cache, aucun nouveau mécanisme de session serveur.

**Tests bloquants :** matrice anonyme/expiré/révoqué/inactif/mauvais tenant/usurpation GUID ; participant autorisé/non-participant ; hiérarchie sans élargissement ; toutes opérations REST et pièces ; sockets après révocation ; délégation expirée/changement de profil/absence de permission. Instances BFF multiples avec même registre, panne Redis sans fallback, anciennes/nouvelles versions refusant explicitement les contrats incompatibles. Les tests middleware actuels démontrent la lacune /list mais ne constituent pas cette recette complète.

**Décisions à approuver séparément :** principal interne signé et anti-rejeu ; registre Redis/sessionId et politique d'indisponibilité ; reconnexion obligatoire des sessions historiques ; table de permissions métier exacte ; délégation intégrateur distincte et audit. Sans accord, aucun de ces changements n'est appliqué.

## Lot 4 — reprise ciblée d'un provisioning interrompu

**Constat :** le verrou advisory actuel sérialise bien deux processus, mais catalogue Master, CREATE DATABASE, cache et bootstrap ne forment pas une transaction distribuée. Le flag `createDb.created` ne permet pas de distinguer une nouvelle base interrompue d'une base historique. Ne pas rejouer le bootstrap en se fondant uniquement sur le nom, le rôle, l'absence de tables ou une erreur previous-run.

**Recommandation :** journal durable de provisioning dans Master, indépendant du schéma métier tenant. Minimum : opération UUID, tenant, étape, version de bootstrap, empreinte de configuration sans secret, nom/OID de base, rôle propriétaire, preuve de création, dates, dernier diagnostic non sensible, numéro de tentative/fencing. Une nouvelle allocation doit être enregistrée **avant** CREATE DATABASE. Une seule opération active par tenant ; une contrainte Master explicite devra être approuvée/migrée séparément.

| État durable | Admission / reprise |
|---|---|
| ALLOCATED | Nom réservé, absence de base confirmée sous verrou. Créer uniquement si toujours absente. |
| CREATING | CREATE DATABASE demandé. Issue incertaine => réconciliation manuelle tant qu'aucune preuve fiable n'est enregistrée. |
| CREATED | OID/propriétaire/config et marqueur d'opération vérifiés. Seule une base de cette opération encore vide peut passer en bootstrap. |
| INITIALIZING | Interruption : si aucun objet métier, reprendre uniquement avec preuve complète ; si schéma intégral compatible, vérifier en lecture seule et poursuivre ; si schéma partiel, intervention manuelle. |
| VERIFIED | Métadonnées compatibles et étape de bootstrap terminée. Autoriser publication cache idempotente. |
| READY | Tenant prêt ; futures ouvertures existing uniquement. |
| FAILED / REVIEW_REQUIRED | Diagnostic durable ; aucune promotion/DDL automatique sans reclassification sûre. |

**Preuve de propriété :** marqueur d'opération non secret associé à la nouvelle base (par exemple commentaire administratif de base avec UUID/version, plus OID dans Master), sous le même contrôle de provisioning. Vérifier systématiquement OID, propriétaire, UUID et empreinte. Un marqueur manquant/contradictoire ou une base remplacée => revue manuelle. La fenêtre entre CREATE DATABASE et enregistrement/marquage reste explicitement incertaine ; ne pas prétendre la rendre atomique. Aucune annotation d'une base historique pour la faire passer artificiellement pour une nouvelle.

**Verrouillage :** conserver la clé advisory Master tenant déjà exercée entre deux processus pendant toute unité de provisioning. Les transitions du journal doivent être commitées durablement dans des transactions dédiées, distinctes de la transaction tenant et du verrou englobant ; une erreur ultérieure ne doit pas effacer la preuve d'une création déjà accomplie. Contrôles compare-and-set sur opération/étape/version à chaque transition, vérification que le verrou est encore possédé avant tout nouvel effet externe. Perte de connexion/verrou ou commit incertain => arrêter, pas de replay automatique. Le détail des connexions Master et du journal nécessite validation de conception avant code.

**Idempotence :** cache publié seulement après VERIFIED ; READY ne réinitialise rien. Reprise de publication cache possible après vérification Master/tenant, sans DDL. Création rôle/extensions et bootstrap vérifient leur appartenance à l'opération ; collisions de nom/configuration non traitées comme succès. Respecter single-flight/générations V01 ; changement de configuration coordonné, jamais réutilisation de l'ancien pool. Ni sync en existing, ni alter/force de rattrapage, ni réparation silencieuse des tables partielles.

**Bases historiques :** absence de journal de création prouvé => existing, contrôles de compatibilité uniquement. Base d'une autre opération, partielle inconnue, OID changé, rôle inattendu, données présentes sans provenance ou schéma différent => REVIEW_REQUIRED. Aucune destruction automatique, même si une création est récente. La migration MemoReads reste un outil explicite séparé ; elle ne sert pas à achever arbitrairement un bootstrap partiel.

**Tests :** crash/erreur à chaque transition, deux processus sur même tenant et deux tenants simultanés, cache indisponible puis reprise, succès de DDL mais réponse perdue, base homonyme historique, marqueur d'une autre opération/OID remplacé, schéma partiel et complet, perte de verrou, version de bootstrap différente ; prouver zéro DDL pour historique et zéro DROP dans tous les chemins.

**Décisions à approuver séparément :** journal/contrainte Master et migration dédiée, marqueur administratif de base, transitions/verrou et transactions de journal, politique explicite de revue manuelle des états incertains. Le correctif actuel conserve donc le test de reprise rouge.
